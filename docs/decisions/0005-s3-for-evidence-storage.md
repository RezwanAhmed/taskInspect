# ADR-0005: S3 for Evidence Storage

- **Status:** Accepted
- **Date:** 2026-09-30

## Context

Workers attach photos as evidence, often several per task and often
taken offline. Reviewers must be able to open them later. Photos are
large compared with the rest of the data, and storing them in
PostgreSQL would bloat the database, slow down backups and put heavy
uploads through the API server. Evidence may show private sites, so it
must never be publicly readable.

## Decision

Store evidence files in **AWS S3** and keep only their metadata in
PostgreSQL.

- **Upload** — the app compresses the photo on the device, then asks the
  backend for a **pre-signed upload URL**. The backend checks that the
  user is the assigned worker, and that the file type (JPEG / PNG) and
  size are allowed, and returns a URL valid for a few minutes for one
  specific storage key. The app uploads the file **directly to S3**,
  then the backend records it as uploaded.
- **Metadata** — the `evidence` table stores the file ID, task ID,
  requirement ID, storage key, file type, file size, created time and
  upload status. Storage keys are generated by the backend (for example
  `tasks/{taskId}/{evidenceId}.jpg`), never taken from the client.
- **Viewing** — reviewers get short-lived **pre-signed download URLs**.
  The bucket is private, blocks public access and encrypts files at
  rest.
- **Offline** — photos wait in local files and the photo upload queue
  until a connection is available (see ADR-0004); they are uploaded
  before the operations that depend on them.
- **Abstraction** — the backend talks to storage through a small
  `filestorage` module, so tests and local development can use an
  S3-compatible replacement instead of real AWS.

## Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| **AWS S3 with pre-signed URLs** (chosen) | Built for large files; very durable; cheap; uploads bypass the API server; fine-grained, time-limited access; standard skill for cloud roles. | Needs AWS setup and credentials; one more service to test against. |
| Files in PostgreSQL (`bytea`) | Everything in one place; one backup. | Database grows quickly; slower queries and backups; all traffic goes through the API. |
| Files on the backend server's disk | Simple to start. | Lost when a container is replaced; does not work with several backend copies; backups are manual. |
| Upload through the backend to S3 | Backend sees every byte and can validate the content. | Doubles the traffic and memory use on the API server; slower on weak mobile connections. |
| Firebase Storage / Google Cloud Storage / Azure Blob | Similar features. | The rest of the cloud setup is on AWS (see the tech stack); no advantage here. |

## Consequences

- The API server stays light; large uploads go straight from the phone
  to S3.
- The backend needs AWS credentials from environment variables, and an
  IAM policy that only allows access to the evidence bucket.
- Uploads that were authorized but never completed leave metadata in a
  pending state; a cleanup job (and an S3 lifecycle rule) removes them.
- The real S3 integration is built in Phase 8 (tasks 8.1-8.3). Until
  then, evidence metadata and the upload endpoint (task 5.17) work
  against the `filestorage` abstraction.
